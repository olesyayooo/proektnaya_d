# Library backend

Modules: `auth`, `books`, `loans`, `readers`. Each module has repository/service dependencies. Issuing, returning and reader history endpoints are implemented.

## Database

For an existing database, run `migrations/001_library.sql` once before starting the new backend, for example with `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/001_library.sql` (use a PostgreSQL URL, without the SQLAlchemy `+asyncpg` suffix). The migration adds unique numeric reader cards to existing readers and creates books, copies and loans. Back up production data before schema changes.

A fresh database is initialized by the existing `create_all` startup. Reader cards are generated during registration; only conflicts on `uq_users_reader_card` trigger regeneration (up to 20 attempts). Librarian responses omit the field.

## API

Paths are relative to the API root. `/auth/me` requires a Bearer token. Catalog and book details are public; an optional valid librarian token enables loan details. Missing or invalid tokens are treated as anonymous on these two endpoints.

- `GET /auth/me`: profile; `reader_card` is optional and included only for readers.
- `GET /books?search=Толстой война&available=true&skip=0&limit=20`: paginated catalog. Each word must match either title or author, ignoring case and word order. Exact title/author matches rank first, followed by stable title/ID ordering. This is token search, without typo correction or stemming. `available=false` includes books with no copies. Limit: 1–100.
- `GET /books/{uuid}`: title, author, publication year, publisher, current availability. Librarians additionally receive `active_loans`, including copy/reader/librarian IDs and dates; readers never receive loan information. A missing book returns 404.

Availability means at least one copy has no loan with `returned_at IS NULL`. Overdue loans still occupy a copy. A partial unique index prevents two active loans for the same copy. Dates use timezone-aware timestamps and a calendar due date. Book copies must be added through database tooling until management endpoints exist.

Run checks from `backend`: `.venv/bin/python -m unittest discover -s tests -v`.

## Readers and loan history

- `GET /readers?reader_card=3595283433`: exact reader card lookup, librarians only. Returns reader ID, name, email and card. Missing reader: `404 READER_NOT_FOUND`.
- `GET /readers/{reader_id}/loans?status=active&overdue=true`: reader history, librarians only. Reader accounts receive `403 LIBRARIAN_REQUIRED`.
- `GET /loans/me?status=active`: authenticated user's own history; the reader ID always comes from authentication.

History lists include book ID/title/author/year/publisher, reader ID/name/card, copy ID, loan dates, status, overdue and overdue_days. All history routes support independent optional `status` and `overdue` filters, `skip` (default 0) and `limit` (default 20, maximum 100); `total` is the count after filtering. Without filters, all loans are returned, newest first.

`status` now accepts only `active` (not returned, including overdue loans) or `returned`. The previous `status=overdue` filter is replaced by `overdue=true`. `overdue_days` is max(0, end_date - due_date) in calendar days: end_date is today's date for active loans or the actual return date for completed loans, using Europe/Moscow. Returning on the deadline is not late. Completed loans keep their final number of overdue days. `overdue` is true when overdue_days > 0. No database migration is needed.

`GET /loans` lists all loans for librarians only. Examples:

- `/loans?status=active&overdue=true`: still on hand and overdue.
- `/loans?status=returned&overdue=true`: returned late.
- `/loans?overdue=false`: active or returned without lateness.

The same filters apply to `/loans/me` and `/readers/{reader_id}/loans`. Every loan response, including issuing, returning and active loans on librarian book details, includes `book`, `reader`, `status`, `overdue` and `overdue_days`. Anonymous book details never expose loans or reader information.

## Issue and return (librarians only)

`POST /loans` accepts:

```json
{
  "book_id": "UUID from the catalog",
  "reader_card": 3595283433,
  "due_date": "2026-11-27"
}
```

Returns 201 with the loan ID, selected copy ID, reader/librarian IDs and dates. The librarian is taken from authentication, and the issue timestamp is generated by the server. Due date may be today (Europe/Moscow) or later. A free copy is chosen automatically and locked with `FOR UPDATE SKIP LOCKED` during creation; the partial unique index additionally prevents concurrent loans of the same copy.

`POST /loans/{loan_id}/return` needs no request body and returns 200 with the updated loan. The return timestamp is generated by the server; a conditional update prevents duplicate returns. Issuing and returning immediately affect catalog availability and reader history.

Errors use `detail: {success: false, message, error}`:

- 400 `INVALID_DUE_DATE`: return deadline is in the past.
- 404 `BOOK_NOT_FOUND`, `READER_NOT_FOUND`, `LOAN_NOT_FOUND`.
- 409 `NO_AVAILABLE_COPIES`: all copies are loaned or currently being issued.
- 409 `COPY_ALREADY_LOANED`: concurrent issue conflict; retry the request.
- 409 `LOAN_ALREADY_RETURNED`: the loan is already closed.
- 401 without authentication; 403 `LIBRARIAN_REQUIRED` for readers.

Existing tables support these actions without another migration.

## Integration with 1C

`POST /integration/purchases` imports purchased editions and physical copies. See [local setup, JSON contract and retry behavior](src/integration/README.md). Example: [1c_purchase.json](examples/1c_purchase.json). Requires the `X-Integration-Key` header matching `INTEGRATION_API_KEY` in `.env`, without a user token. The new `purchase_imports` table is created at startup or via `migrations/002_purchase_imports.sql`.
