# Приём поступлений из 1С

Код модулей 1С, состав метаданных, пошаговая настройка Конфигуратора macOS и
проверка PostgreSQL: [интеграция 1С 8.5](../../integration_1c/README.md).

`POST /integration/purchases`, JSON UTF-8, авторизация `X-Integration-Key: <ключ интеграции>`.

Для локального запуска из папки `backend`:

```sh
.venv/bin/python -m uvicorn main:app --host 127.0.0.1 --port 8000 --reload
```

При запуске создаётся новая таблица `purchase_imports` (в ней хранится результат загрузки каждого документа). Для ручного создания есть `migrations/002_purchase_imports.sql`.

1. В `backend/.env` взять значение `INTEGRATION_API_KEY` и указать его в настройках обмена 1С. Ключ уже сгенерирован локально; `.env` исключён из Git.
2. Перезапустить backend после изменения `.env`.
3. Отправить документ на `http://127.0.0.1:8000/integration/purchases`, передав заголовки `X-Integration-Key: <значение INTEGRATION_API_KEY>` и `Content-Type: application/json`.

Ключ постоянный, без срока истечения. Вход библиотекаря и JWT для этого маршрута не нужны. Чтобы сменить ключ, измените его в `.env` и настройках 1С и перезапустите backend.

Здесь указан адрес прямого запуска uvicorn. Настройка `root_path="/api"` предназначена для прокси; сама по себе она не добавляет `/api` к маршрутам прямого сервера.

Пример документа — `examples/1c_purchase.json`. Проверка без 1С из терминала в папке `backend`:

```sh
curl -X POST http://127.0.0.1:8000/integration/purchases \
  -H 'X-Integration-Key: ВСТАВИТЬ_КЛЮЧ_ИЗ_ENV' \
  -H 'Content-Type: application/json' \
  --data-binary @examples/1c_purchase.json
```

`document_id` — стабильный уникальный идентификатор документа поступления в 1С, лучше UUID ссылки документа, а не отображаемый номер. При повторе запроса 1С должна передавать тот же ID. В одной базе 1С и на одном компьютере этого достаточно; при подключении нескольких баз нужно добавить идентификатор источника.

`books` — от 1 до 100 строк. В строке обязательны `title`, `author`, `publication_year`, `publisher`, `quantity`. Количество — целое от 1 до 1000; всего не более 5000 экземпляров на документ. Неизвестные поля отклоняются. Цена и сумма покупки пока не принимаются.

Издание сопоставляется по точному совпадению названия, автора, года и издателя после удаления пробелов по краям. Другой год/издатель создаёт другую запись книги. При совпадении создаются только экземпляры. Регистр и внутренние пробелы должны быть одинаковыми; внешние ID номенклатуры 1С пока не сопоставляются.

Ответ 200: `success=true`, в `data` — `document_id`, `already_imported`, `created_books`, `created_copies`, список `books` с `book_id` и количеством. При повторе того же документа возвращается прежний результат с `already_imported=true`, новые экземпляры не добавляются. Счётчики в повторном ответе относятся к первоначальной загрузке. Порядок строк не влияет на сравнение, одинаковые строки суммируются.

Изменённый документ с уже использованным ID: 409 `PURCHASE_DOCUMENT_CONFLICT`. Исправление/отмена проведённых поступлений пока не реализованы; не нужно подменять ID ради повторной загрузки исправленного документа, это добавит экземпляры повторно.

Без ключа или с неверным ключом — 401 `INVALID_INTEGRATION_KEY`; если ключ не настроен на backend — 503 `INTEGRATION_NOT_CONFIGURED`; неверная структура — 422. При ошибке записи весь документ откатывается. Параллельные поступления в PostgreSQL сериализуются транзакционной advisory-блокировкой; ID документа также защищён уникальным ограничением.

Важно для 1С: HTTP-запрос должен выполняться на том компьютере, где работает backend. В клиент-серверной 1С серверный вызов к `127.0.0.1` обращается к серверу 1С, а не к компьютеру клиента.

Роутер находится в `backend/src/integration/router.py`, обработчик — `import_purchase`. Подключён в `backend/src/routers.py`. Swagger при прямом запуске: `http://127.0.0.1:8000/docs`, раздел `integration`; для ключа используется кнопка Authorize и поле X-Integration-Key.

## Отчёт о просрочках для 1С

`GET http://127.0.0.1:8000/integration/overdue-report`, заголовок `X-Integration-Key` тот же, что у поступлений. JWT и вход в аккаунт не нужны. Запрос только читает данные.

Параметры:

- `status=active` (по умолчанию): текущие просроченные выдачи на руках.
- `status=returned`: сданные с опозданием.
- `status=all`: оба варианта.
- `skip=0`, `limit=100`: пагинация, максимальный limit — 1000.

```sh
curl 'http://127.0.0.1:8000/integration/overdue-report?status=all&skip=0&limit=100' \
  -H 'X-Integration-Key: ВСТАВИТЬ_КЛЮЧ_ИЗ_ENV'
```

Ответ: `success`, массив `data`, `total` (всего после фильтра), `skip`, `limit`. Элемент data содержит ID выдачи (`id`), `copy_id`, `reader_id`, `librarian_id`, `issued_at`, `due_date`, `returned_at`, `status`, `overdue=true`, `overdue_days`, вложенные `book` (ID, название, автор, год, издательство) и `reader` (ID, имя, читательский билет). Пароли не возвращаются.

Для активных выдач дни просрочки считаются до сегодняшней даты по Москве, для сданных — до фактической даты возврата по Москве. В день срока возврата просрочки ещё нет. Возвращаются только записи с просрочкой больше нуля.

Для загрузки всего отчёта 1С должна запрашивать страницы, увеличивая skip, до получения total записей. Порядок — сначала новые выдачи, затем ID. Отчёт отражает текущее состояние базы, страницы не являются сохранённым снимком: если параллельно выдавать или возвращать книги, данные могут измениться. При отсутствии просрочек возвращается 200, `data=[]`, `total=0`.

Для обновления данных в 1С используйте ID выдачи, чтобы повторная загрузка не создавала дубликаты. Если 1С хранит текущие просрочки, при синхронизации нужно также учитывать исчезновение записей из отчёта активных просрочек после возврата.
